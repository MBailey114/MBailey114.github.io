AI-powered self-serve dashboards

Sky, 2025 – present · Built solo · Next.js, Python, custom MCP, OpenAI (GPT), OpenSearch

The problem

Non-technical users across Sky's departments relied on business analysts to file change requests against a fixed set of monitoring dashboards I'd owned for the previous three years. Turnaround could be days. The available set of views never quite matched what individual users actually wanted, so they either compromised or stopped asking.

Approach

I built a natural-language chat interface on top of the existing dashboard system. Users ask things like "show me 4G usage split by tech in a stacked bar chart over the last eight months"; a custom agent parses the intent, queries OpenSearch through a custom Model Context Protocol (MCP) server, and returns a chart widget. The user can add the chart to their own dashboard, resize it, and position it however they like. Over multiple queries they assemble a dashboard tailored to their own work. No change requests, no BA loop.

Why a custom agent orchestrator

Sky has an internal AI gateway that didn't support tool-calling in the form I needed. Rather than shoehorn my design into its limitations, I wrote a minimal orchestrator directly on top of the raw chat-completion API. The system runs on OpenAI's GPT models (chosen over Claude for cost) and the MCP layer stays cleanly separated, so swapping providers later is a config change.

Stack

  • Frontend: Next.js, React, TypeScript. Chart rendering, drag-and-drop widget layout.
  • Agent layer: Python. Custom MCP server exposing data tools. Custom agent orchestrator on OpenAI GPT models.
  • Data: OpenSearch (the same data backbone as the pre-existing dashboards).
  • Middleware: GraphQL, reused from the existing dashboard stack.

Where it stands

Pre-rollout hardening. Demoed to three stakeholder groups so far: Sky's data engineering team, another Sky observability team, and a set of Comcast executives (Sky's parent company). The director is using the project as an anchor for a broader shift in the department toward agentic workflows, which has included me running onboarding sessions on effective and safe AI use across engineering and non-engineering work.

What I owned

  • The frontend UI and widget system
  • The custom MCP server and the agent orchestrator
  • Integration against OpenSearch and the existing GraphQL middleware
  • The demos and onboarding sessions driving adoption

Clinical-Trials Agent: grounded research assistant for ClinicalTrials.gov

Side project, 2026 · FastAPI, LangGraph, Next.js 16, OpenAI (gpt-5.5 / 5.4-nano), Postgres, Redis · Live · Source

The problem I was solving

With medical data, a model that makes things up is dangerous. A wrong trial phase or eligibility rule, stated as fact, is misinformation. I wanted a grounded agent that can only answer from data its tools actually retrieved, backs every fact with a citation the server verifies, and still reads as plain language for a non-technical reader. ClinicalTrials.gov's public v2 API gave me a rich, messy, real-world source to build against.

Approach

It's a dual-stack app. A FastAPI and LangGraph backend runs the agent and a deterministic retrieval funnel, and a Next.js 16 frontend renders the conversation, citations, charts, and a full-result-set research workspace. The agent is a bounded tool-calling graph (capped at 5 model steps so it always finishes) with four typed tools:

  • searchClinicalTrials: runs the full funnel and returns a small set of ranked, token-bounded study cards. This is the only data the agent is allowed to answer from.
  • getStudyDetail: the full record of one trial (sponsor, endpoints, arms, eligibility, dates). On a bad id or upstream failure it returns a structured error instead of ending the turn.
  • refineWithinResults: slices, counts, or sorts within a previous search's full result set by run id, with no new registry call. This powers phase breakdowns and "of those, which are Phase 3?" follow-ups cheaply.
  • crossReferenceCompanyPipeline: fetches a company's public R&D pipeline page, extracts the assets with the model, and lines them up against trials already retrieved, kept separate from registry fact.

The grounding contract (the core idea)

The agent can only state facts from studies its tools returned that turn. Every claim is tagged with a compact [NCT_ID#section] anchor that the UI renders as a clickable citation pill and that the server checks against the retrieved set, so a made-up trial id gets caught instead of shown. The same check covers the visuals: the agent emits inline chart directives like [chart:timeline|…], [chart:compare|…], and [chart:facets:phase] that the frontend draws from the same retrieved set (hand-written SVG and CSS, no charting library). A reference to a trial it didn't retrieve falls back to a small warning rather than inventing data.

Hybrid retrieval funnel (no LLM ranking)

A five-stage funnel keeps answers fast, bounded, and reproducible. It pages field-projected candidates from the registry under a time budget, scores them with a deterministic lexical signal (condition and title overlap plus a status bonus), optionally blends in a semantic signal from cached embeddings, then keeps the top few, hydrates the heavy fields only for those, and trims each card to a token budget. No model is used to rank. A cheap model only writes a one or two sentence per-study summary, clearly labelled as not a source fact, and the semantic step falls back to pure lexical if it's disabled or runs over budget.

Resumable streaming and durable history

Generation runs in a background task that writes every streamed frame to Redis, so a refresh or a dropped connection mid-answer reconnects to the same run, replays what it missed, and tails the rest. The reconnected answer is identical to one that was never interrupted. Postgres is the durable record (conversations, messages, runs, and the LangGraph state for multi-turn context), and any runs left hanging by a crash are reconciled on startup.

Stack and deployment

  • Backend: Python, FastAPI, LangGraph, with Postgres for history and Redis for the live-stream buffer and explorer snapshots.
  • Frontend: Next.js 16, React 19, Vercel AI SDK v6, Tailwind 4, with every chart hand-built in SVG and CSS.
  • Deployment: the frontend runs on Vercel and the backend runs as a container on Fly.io in London, next to managed Neon Postgres and Upstash Redis. Co-location matters here, because every token passes through the Redis buffer, so an early US/EU split made streaming crawl until I moved compute into the same region. It runs as an open demo, so OpenAI spend is capped by per-IP rate limits, a global daily limit, input-size limits, and the OpenAI monthly cap rather than a login, and each browser gets its own private history.

What I'd do next

Add real sign-in to replace the current tenant header, which is a trusted but forgeable placeholder (the seam for it is already there). Add a bot check such as Turnstile as another step in front of the model, alongside the rate limits. And move off startup schema creation to a proper migration tool if it ever grew past a demo.

Ask F1: conversational F1 dashboard and race-replay viewer

Side project, 2026 · Next.js 16, React 19, Vercel AI SDK v6, OpenAI (gpt-5.5 / 5.4 / 5.4-nano), TypeScript · Live · Source

The problem I was solving

I wanted to learn the Vercel AI SDK end-to-end and have a public artifact that demonstrates the same agent-orchestration pattern I'd shipped at Sky, without proprietary code. F1 was a good fit for the data layer (Jolpica's free Ergast-successor API covers 1950–today, OpenF1 has rich telemetry for the current season) and gave me a clean excuse to build something more visually arresting than another LLM chatbot demo.

Approach

Two surfaces, one Next.js process, no agent framework.

  • Dashboard (/): chat agent with 6 typed Zod tools (query_f1, add_widget, remove_widget, replace_widget, relayout_dashboard, compose_dashboard) that mutate a 12-column grid in real time through a Zustand store. compose_dashboard takes a single themed prompt ("build me a Hamilton 24 vs 25 deep-dive") and returns 4–6 cohesive widgets in one streamed call. Click any widget for a scoped chat where the widget's data is pre-grounded in the system prompt and a Tavily web-search tool answers "why" questions with cited sources.
  • Race replay viewer (/tracks): pre-baked 2025 lap telemetry (OpenF1 location + car_data joined on nearest timestamp, mini-sector boundaries derived from sector segment data) replayed at 60Hz. Cars trace the racing line via Catmull-Rom spline interpolation over 10fps location samples. Multi-driver speed/throttle/brake chart below; clickable mini-sector arc segments scope playback to a corner. A live AI race-commentary HUD overlays the track, firing on each mini-sector crossing during playback, with topic-rotation logic and entity-blocklist extraction so the model varies the angle and avoids repeating drivers or topics across 30 lines of a lap.

Custom agent step timeline

I wasn't satisfied with how most LLM chat UIs render tool calls: a single line per tool with no inspection. So I built a custom timeline: every tool call appears as a step card with index gutter, label, duration, state badge, and a click-to-expand inspector. Each tool gets a tailored output renderer (record count + field chips for query_f1, mini widget-card for add_widget, column-strip pills for relayout_dashboard, source citations for web_search). Once the message settles, the whole timeline auto-collapses to a single pipeline pill (▸ 5 steps · F1 › +W › +W › +W › ▤ · 1.82s · ✓) so old conversations stay tight; click to re-expand.

Stack

  • Frontend: Next.js 16 (App Router) + React 19 + TypeScript strict, Recharts 3, Tailwind 4. Zustand 5 with persist + selector subscriptions for hot-path state.
  • AI: Vercel AI SDK v6 (streamText, generateObject, useChat with custom DefaultChatTransport). Three OpenAI model tiers: gpt-5.5 (agentic dashboard chat, 6 tools, stopWhen: stepCountIs(8)), gpt-5.4 (scoped widget/track chat with web search), and gpt-5.4-nano (suggestions + race commentary at high request volume).
  • Data: Jolpica F1 (Ergast successor, no auth) for 1950–today historical data; OpenF1 for current-season telemetry (used at pre-bake time only). Three-layer architecture: server flattens nested JSON, AI specifies a chartConfig, client pivots to Recharts wide format. The model never sees the records array, only field names plus three sample rows.
  • Infra: Edge runtime on every API route. Next's data cache (fetch(url, { next: { revalidate: 300 } })) layered on top of an in-process Map for cross-invocation persistence. Race replays pre-baked into static JSON to bypass OpenF1 free-tier rate limits during demo.

Things I built that I'm proud of

  • compose_dashboard tool: one LLM call returns a typed array of 3–8 widgets with cols 1–12 per widget. Client-side packRows() defensively pads under-filled rows so the AI doesn't have to be perfect at arithmetic. 10-second undo toast restores the prior dashboard if the user regrets a generative replace.
  • Performance discipline on the tracks page: diagnosed and fixed three independent 60Hz hotspots: a LiveLeaderboard sort that re-ran every frame (now invariant-aware), a Recharts ReferenceLine that forced the whole chart tree to re-render per tick (extracted into a standalone overlay div that mutates style.left), and a Zustand subscription that allocated a lap-key string per tick (replaced with numeric identity check). Chart re-renders dropped from ~60/sec to 0/sec.
  • Cross-invocation cache fix for Vercel Edge: production was hitting 504s on widget loads because the in-memory Map cache only worked intra-process. Layered Next's revalidate: 300 data cache so cached responses persist across isolates.
  • Driver-mention chips: driver names in any chat reply auto-render as 16px portrait chips with hover popover (full name, team, code). Reused across the dashboard chat, scoped widget chat, and race-commentary feed via a single segmenting helper.

What it doesn't have, deliberately

No auth, no DB, no mobile responsive, no agent framework, no MCP server. The whole "orchestrator" is the Vercel AI SDK plus ~30 lines of pivot logic. Token usage stays low because the model only ever sees a schema preview; chart output stays deterministic because the pivot is pure TypeScript, not LLM-generated.

Internal monitoring dashboards

Sky, 2022 – present · Next.js, React, GraphQL, OpenSearch, TypeScript

The problem

Multiple Sky departments needed visibility into operational data such as telecoms usage, service health, and platform metrics. Raw OpenSearch queries weren't practical for non-technical stakeholders, and product teams and operations needed curated, reliable views they could lean on day-to-day.

Approach

Full-stack dashboards built iteratively with each department as a stakeholder. Next.js / React on the frontend, a typed GraphQL middleware layer, OpenSearch as the data backbone. The dashboards grew in scope over three years as more teams asked to be served by them.

Outcome

In active use across Sky. The dashboards became the launchpad for the AI self-serve work: the pain of the BA-mediated change-request process directly motivated building something users could steer themselves.
